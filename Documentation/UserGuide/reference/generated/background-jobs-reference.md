# Background Jobs and Recurring Queries

Background Jobs run long SELECT/CTE queries without blocking the interactive ULP menu. On the shared **Use query** screen choose **Run in background**, then open **Background jobs** from the main menu or Options.

Recurring queries repeat a reviewed SELECT/CTE at a fixed interval. On **Use query**, choose **Run on a schedule**, configure an interval such as `30s` or `5m`, optionally set a run limit, then use **Recurring queries** to inspect, pause, resume, or cancel it. The first run can start immediately or after one interval.

## Supported output

Jobs accept `Format -> File` pipelines and the `NONE` destination. Standard output, Spectre Console, the Text User Interface (TUI), DataGrid-style viewers, and other terminal-owned destinations are rejected. ULP asks you to choose a File format/destination or NONE; it never silently redirects output.

Each job captures its SQL, bound parameters, source definitions, connection string, formatter settings, output paths, and execution options at submission time. Sensitive parameter values are not shown by Job Manager, and displayed SQL/diagnostics use the normal masking helper.

## Concurrency and SQLite

The default limit is two concurrent jobs and can be changed under **Options > Change runtime settings** or with `--max-background-jobs`. Excess work remains Queued. Each job uses an isolated SQLite session and recreates the configured ParsingModule virtual tables. Temporary tables or views created only in the foreground session are therefore not available to a background job.

## Cancellation, progress, and files

Cancel propagates to `SQLiteCommand.Cancel`, row enumeration, formatters, and destination writing. Queued jobs cancel without starting. Cancellation is reported as Cancelled, not Failed. One-time background jobs cannot pause. A recurring schedule can pause: a running query finishes, then no new run begins until resume. Paused and waiting schedules occupy no background execution slot, and a schedule never overlaps itself.

Job Manager reports rows processed, bytes written when available, queue/query/output durations, output paths, and concise failures. No percentage is shown because ordinary SQLite/ParsingModule queries do not expose a defensible total-row denominator.

File output is written to a temporary `.partial-*` sibling. The requested final filename is published only after successful completion. Failed and cancelled partial files are deleted. Active jobs reserve their normalized destination paths, so another job cannot write the same file concurrently; use a filename such as `events-{yyyy-MM-dd-HHmmss}-{JobId}-{RunNumber}.csv` for naturally unique scheduled exports. `{RunNumber}` starts at 1 for each schedule.

## Attached CLI recurrence

The ordinary CLI can repeat a query while remaining in the foreground:

```powershell
ulp --query "SELECT datetime('now') AS checked_at" --every 30s --runs 10
```

The first run is immediate unless `--wait-first` is supplied. Terminal, File, and NONE output remain available. `--continue-on-error` advances to the next interval after an error; otherwise the first nonzero run stops the command. Ctrl+C cancels the current query or wait and exits with code 130. This is an attached process, not a durable service or detached cron daemon.

## Live tail

`--tail` follows one local file through the `TextLine` provider and runs the same SQL against each newly completed group of lines. It uses a process-memory checkpoint, polls every second by default, and ignores the unfinished trailing line until its newline arrives. Existing complete lines are skipped unless `--tail-existing` is supplied.

```powershell
ulp --input TextLine --from C:\Logs\application.log --table logs `
    --query "SELECT Text FROM logs WHERE Text LIKE '%ERROR%'" --tail --every 500ms
```

Tail mode is polling rather than a filesystem notification service. It handles ordinary append, truncation, and replacement detection, but it is process-scoped and provides at-least-once processing around abrupt process termination—not a durable exactly-once delivery guarantee. Ctrl+C stops it. Tail currently accepts exactly one seekable local TextLine file; globs, URLs, and archive members remain normal batch inputs. Use `{RunNumber}` for recurring file-output names.

## Lifetime

Jobs, schedules, and completed history are application-scoped and live only in the current interactive ULP process. Exiting cancels every schedule so no future run can start, then handles any still-cancelling background query. History is not persisted across restart.

Detached `ulp ... --background` and cross-process `ulp jobs ...` commands are intentionally not exposed in this model: returning from a short-lived CLI process would terminate its jobs. A persistent authenticated worker/registry is required before those commands can be truthful and safe.
