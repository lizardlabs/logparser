# Static PE and CLR metadata for managed .NET DLL and EXE files: -i=DotNetAssembly

## Description

Static PE and CLR metadata for managed .NET DLL and EXE files. Command line switch to use this input format is -i=DotNetAssembly.

**Category:** Software artifacts
**Aliases:** `Assembly`, `DotNet`

This provider statically inspects PE and CLR metadata in managed `.dll` and `.exe` files. It uses metadata readers only: inspected assemblies are never runtime-loaded, resolved, or executed. Native PE files and malformed CLR metadata are rejected rather than treated as managed assemblies.

The default `Assembly` view returns one summary row per file. Set `View` to `References`, `Types`, `Methods`, `PInvokes`, `Resources`, or `Attributes` to create a related virtual table over the same files. This matches ULP's one-stable-schema-per-virtual-table model.

## Data Provider

Use local `.dll` or `.exe` paths and glob patterns. `Recurse` controls directory traversal. Extension is only a candidate filter: the provider also requires a valid PE structure, CLR header, and assembly metadata manifest.

```sql
CREATE VIRTUAL TABLE assemblies USING ParsingModule('.\bin\*.dll', '-i:DotNetAssembly');
CREATE VIRTUAL TABLE assembly_refs USING ParsingModule('.\bin\*.dll', '-i:DotNetAssembly -View:References');
SELECT AssemblyName, AssemblyVersion, TargetFramework, Architecture, SHA256 FROM assemblies;
SELECT ParentFile, AssemblyName, Version, PublicKeyToken FROM assembly_refs;
```

Reference rows are manifest declarations, not proof that a dependency exists on disk. `StrongNameSigned` reports the CLR header flag and `StrongNameValidationStatus` states explicitly that no cryptographic verification was performed. Authenticode presence is likewise distinct from signature or trust validation. License fields are populated only from explicit assembly metadata; copyright, company, and product text are never treated as a license. An `EmbeddedLicenseResource` name is evidence that a clearly named resource exists, not a legal classification of its contents.

## Related metadata views

Each `View` has a stable schema. `References` exposes declared assembly dependencies; `Types` exposes kind, visibility, inheritance, and generic arity; `Methods` exposes decoded signatures and bounded body statistics; `PInvokes` exposes native imports; `Resources` exposes metadata and sizes without dumping contents; and `Attributes` exposes assembly-level custom attributes. Create a separate ParsingModule virtual table for each view you need, then join on `FilePath`/`ParentFile`.

Detailed IL instruction disassembly, strong-name validation, Authenticode certificate-chain validation, and external PDB/Source Link loading are not performed by this provider.
